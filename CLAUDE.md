# Préférences globales (tous projets)

## Langue
Toujours répondre en français (orthographe complète, accents respectés).
- Contenu produit (textes UI, copy, descriptions, modales) sans marqueurs « IA » : pas de tirets cadratin ni demi-cadratin en ponctuation (virgule, point, deux-points, parenthèses à la place), pas d'émojis ni d'icônes décoratives, pas de gras emphatique gratuit. Ponctuation simple, phrases qui se lisent. Trait d'union des mots composés admis.

## Sécurité Claude Code (ne pas désactiver)
Poste en autonomie maximale : mode `auto`, barrière par les hooks `PreToolUse` du plugin cliff-stack et `permissions.deny` en filet ; les hooks et les `deny` valent dans tous les modes, les `allow` ne protègent rien. Montage et ce qui interrompt encore : `skills/cliff-stack/hooks/README.md`.
- Ne jamais réintroduire de règles `allow` par projet (inutile, génère des prompts).
- Un hook bloque à tort : corriger le script (`skills/cliff-stack/hooks/scripts/`), jamais le câblage. Écrire hors projet : lancer ce dossier comme projet, ne pas contourner.

## Style de travail
- Tâche non triviale : analyse dense, à la profondeur que le problème exige, l'outcome en premier ; tâche triviale : réponse courte et directe.
- Agir, ne pas demander : ce qui est demandé (correctif, refactor, Write/Edit, y compris sur du code existant) se prouve, s'écrit, se vérifie et se rend compte, sans validation intermédiaire. On ne s'arrête que pour une action irréversible hors du périmètre demandé, ou pour un choix réellement indécidable seul, soumis d'abord à `framing-critic`.
- Une question ou un problème décrit appelle une évaluation : rapporter et s'arrêter, le correctif attend d'être demandé.
- Interfaces : divulgation progressive. Le moins possible à la première vue ; le reste à la demande (menu déroulant, panneau dépliable, infobulle, fenêtre).
- Maquettes d'interface : un canevas Claude Design (artefact « Design », design system du projet quand il en a un, un artboard par état, chaque état en clair et en sombre), jamais une page HTML autonome. Un écran nouveau s'y dessine ; un écran existant ne s'y redessine jamais de mémoire : ses artboards montrent son vrai rendu (HTML modifiable exporté quand le projet le permet, sinon une image), seul l'ajout étant nouveau. Les règles d'un projet précisent l'outil de rendu.
- Git : commit directement sur `main`, jamais de branche sauf demande explicite (prime sur la consigne par défaut du harness).

## Mémoire
- Fichiers de règles (CLAUDE.md, rules, skills, agents ; écrits pour le modèle, relus à chaque session) : une règle nouvelle se fond dans celle de même sujet ou la remplace, au bon endroit de la structure, jamais ajoutée au fil de l'eau ; consignes concrètes et vérifiables ; chaque ligne passe le test « l'enlever ferait-il faire une erreur ? » ; une raison courte quand elle aide à généraliser ; dans CLAUDE.md et rules, aucun exemple sauf pour montrer un format : un nom, une valeur ou une liste cités en exemple, par l'utilisateur ou trouvés dans l'ancienne version, décrivent le besoin et ne s'écrivent pas, la règle dit le besoin (un skill ou un agent garde les exemples que sa doctrine d'écriture demande) ; aucune citation ni argument pour convaincre un humain ; emphase (IMPORTANT, majuscules) sur une seule ligne qui serait ignorée ; ce qui doit toujours arriver passe par un hook ; aucune redite d'une règle globale dans un projet (le projet ne garde que ses outils et ses écarts) ; la taille reste stable dans le temps.
- Mémoire persistante (`~/.claude/projects/.../memory/` et `MEMORY.md`) : avant d'écrire, prouver que le fait n'est capturé nulle part ailleurs, commentaires de code, messages de commit, CLAUDE.md global ou projet, `rules/`, README compris ; un commentaire que je viens d'écrire compte. Dans le doute, ne pas écrire.

## Règles de code
- Code rédigé en anglais (ex: fonction, nommage, commentaire, variables, nom de fichier/dossier etc.).
- Découvrir avant de supposer : sur tout sujet nouveau, identifier le stack réel (technos, conventions, variables, règles du projet) et l'épouser ; code, API et variables natifs du projet plutôt qu'un pattern venu d'ailleurs ou un défaut présumé. Demande ambiguë ou à fort enjeu : restituer ma compréhension en une phrase ou poser une question ciblée, jamais réécrire la demande en silence.
- DRY sans régression : s'appuyer sur le code, les fonctions et les points d'extension du projet, mettre à jour l'existant, aucun doublon. Tout code s'écrit réutilisable : paramétrable, sans état caché, appelable depuis plusieurs endroits ; l'extraction se fait à la deuxième occurrence, jamais avant (règle des 2 occurrences, commentaires, destroy, build : `rules/code-style.md`).
- Rien en dur : aucun nom, chemin ou valeur codé quand une découverte dynamique est possible. Skills, rules et analyses parlent en termes génériques (plugin, thème, arborescence, architecture) : aucune liste blanche ou noire de noms sauf si une source reconnue la justifie, citée. Les noms propres d'un cas restent dans ses tests et ses données.
- Séparer la feature de ses consommateurs (Dependency Inversion) : une feature ne nomme jamais une feature de même niveau ; si A doit connaître B, l'abstraction (registre, point d'extension) monte d'un cran et les deux s'y déclarent. Test avant d'écrire : « si je supprime ce fichier, qu'est-ce qui tombe ? » Si autre chose que lui tombe, le code est au mauvais endroit. Invariants : `rules/architecture-extension.md`.
- Code moderne, minimaliste, performant ; la cause profonde, jamais une rustine. CSS : `rules/css-scss.md` (jamais de Sass).

## Huit portes
Tout changement de comportement les passe dans l'ordre ; les Variations disent lesquelles pour les autres cas. Ces questions viennent de moi, jamais de l'utilisateur.

- (1) Reproduire par déclenchement réel : de vrais gestes (clics, saisies, raccourcis), jamais une simulation programmatique. Vérifier que l'action a eu lieu (horodatage, journal, état) avant de juger son effet : un enregistrement qui n'a pas marqué l'état modifié n'a rien déclenché.
- (2) Localiser la cause dans le code du projet, au niveau que disent ses usages (grep : composant, page, config, framework ; un élément partagé se corrige au niveau partagé), jamais d'après la doctrine ni le seul rapport d'un agent.
- (3) Réfuter par mesure directe : fournir ce qui manque, ça passe ? Un changement composé s'isole par moitiés jusqu'au coupable ; un succès par accident (cache, état régénéré) est un faux positif. Signal sémantique direct, jamais un proxy : le contenu ou l'attribut réellement visé, pas une longueur ni un drapeau approchant ; la plupart des faux bugs viennent d'une sonde imprécise.
- (4) Existant, nécessité, forme : une brique équivalente cherchée avant d'écrire ; le skill ou l'agent dédié au sujet invoqué plutôt qu'improvisé ; la doc à jour par Context7 ; les règles et l'architecture du projet lues avant de placer le code (couches, frontières, points d'extension).
- (5) Failles et oublis sur la nature du sujet : pre-mortem (« si ce changement échoue, pourquoi ? »), même question ailleurs, cas limites, suppositions.
- (6) Manques (ajouter, supprimer, modifier) : proposés avec gain et coût, codés sur accord seulement sauf mention contraire de l'utilisateur, notés sinon.
- (7) Avant de coder, quand le changement crée ou déplace un fichier, touche une frontière ou un point d'extension, ou laisse ouvert un choix de niveau (composant, page, config, framework) : `framing-critic` tente de réfuter (4) à (6) et le plan, conformité à l'architecture comprise ; une objection tenue fait revoir son seul point. Un correctif localisé s'en passe.
- (8) Prouver après, par de vrais gestes : défaut absent ou comportement présent ; écran stable (aucun élément recréé ni animation rejouée pour un état identique, au repos et au survol) ; essais des fichiers touchés verts ; contrôles statiques du projet sans hausse. Un hook Stop refuse « fini » tant que cette preuve manque. Chaque lot rendu part aussitôt chez les vérificateurs de ses niveaux, sans attendre l'utilisateur, avec fichiers touchés, comportement attendu, gestes à rejouer, défaut à reproduire ; d'ici leur rapport, le lot est « en vérification », jamais « fini ».
  - Niveaux, du plus rapide au plus lent : **0** statique (syntaxe, types, lint, vérificateurs du projet), par le codeur ou moi, jamais en fond, zéro hausse sur les fichiers touchés, relancé à chaque lot ; **1** les tests existants des fichiers touchés ; **2** le rendu isolé des écrans touchés (banc, faux hôte, équivalent du projet) : un état amené, rendu, stabilité vérifiée, sans scénario ni banc à entretenir ; **3** le service réel sans interface (API, routes), quand le lot touche le serveur sans l'écran ; **4** le parcours réel dans l'application, un gros lot fini.
  - Niveau 4 exploratoire et silencieux : le vérificateur reçoit le but et le résultat attendu, jamais un scénario ; il lit l'écran (arbre d'accessibilité, DOM), choisit le geste suivant d'après ce qu'il découvre, éléments trouvés par rôle et libellé visibles, jusqu'au résultat ou au blocage ; commandes du projet en tâche de fond, jamais les outils MCP Playwright, dont chaque appel s'affiche. Le chemin trouvé ne se fige en script que sur demande.
  - Isolement : copie ou environnement d'essai (dossier temporaire du projet, port tiré par le système, données d'essai), jamais l'instance, les données, la session ni le serveur de l'utilisateur ; tout ce qui est lancé est arrêté et effacé. L'environnement de séance se prépare une fois, se reprend à chaque lot, jamais relancé de zéro ni tenu par un agent qui attend ; un verdict n'y vaut qu'avec un seul pilote, une copie prouvée à jour pour les fichiers du lot, l'expiration automatique coupée, un état neuf quand le départ compte (sinon dit « sur état accumulé ») ; balayé en fin de séance.
  - Preuve par le contenu, pas par l'image : DOM, état, réponse, fichier écrit. Une capture seulement si l'aspect visuel est la question et qu'aucun signal du contenu ne le dit : une fois, jamais en série ni comparée au pixel, jamais dans git.
  - Tests : les existants et rapides se gardent et se lancent sur les fichiers touchés ; un test cassé par un changement voulu s'adapte au plus court ou s'efface, jamais réécrit de zéro ; un test nouveau seulement pour figer un défaut réel reproduit, ou sur demande.
  - Rapport : verdict et cause en mots simples, corrigé et restant. Une conclusion (fix, cause, « résolu », « n'existe pas ») se rend avec ce qui l'établit, la commande ou le geste et son résultat ; pour une absence, le périmètre fouillé ; aucune autre mesure (écarts, comptes, durées) qui ne décide rien.
  - Chaque projet déclare ses outils par niveau (CLAUDE.md, rules, `.claude/ux-e2e.json` pour le niveau 4) ; un niveau sans outil est sauté et dit dans le rapport. Les règles d'essai d'un projet priment quand elles sont plus strictes.

Après les portes :
- Débogage : un seul changement à la fois, effet observé avant le suivant ; trois correctifs échoués sur le même bug : stop, remonter d'un niveau et requestionner le diagnostic ou l'architecture.
- Critique indépendant (`independent-critic`, qui porte son protocole), seulement dans un de ces cas : zone déclarée critique par les rules du projet, ou code distribué ou partagé entre projets ; action irréversible ou sortante (suppression, push, publication, envoi) ; run long ou autonome sans surveillance ; chantier où plusieurs agents écrivent (lancé dès le départ, réfute chaque rendu) ; cause ou absence qui porte un correctif alors que la porte (1) n'a pas pu être franchie ; demande explicite. Hors de ces cas, ni critique ni « double-check » : le rapport de la porte (8) suffit. Un seul critique, plusieurs seulement pour des zones indépendantes ; un finding non reproduit n'impose rien ; le code ajouté après sa passe lui est soumis avant « fait ».

## Variations
- Défaut signalé : (1) à (8).
- Fonction nouvelle ou refonte : d'abord le résultat attendu, écrit en une phrase vérifiable, celle que (8) prouvera (un écran : sa maquette validée) ; puis par incréments, chacun passant (4) à (8) ; (1) à (3) seulement si elle corrige aussi un défaut.
- Retouche sans effet (texte, libellé, style sans comportement) : (8) seule, par une recherche qui prouve la valeur en place, sans essai ni vérificateur.
- Question ou diagnostic : (1) à (3), puis le rapport ; aucun code tant qu'il n'est pas demandé.
- Équipe (plus d'un agent qui écrit, ou plus de deux agents en tout) : charger le skill `equipe` avant de lancer. La porte (8) est tenue par un seul arbitre des essais pour toute l'équipe, en tâche de fond pendant que je prends les demandes suivantes ; aucun autre agent ne dépasse le niveau 0. Un défaut trouvé sur un lot repart chez un codeur avec le rapport, puis repasse chez le vérificateur ; au troisième échec, stop et retour à l'utilisateur. Je dis à l'utilisateur ce qui a été trouvé et corrigé ; ce qui sort du lot (écart ancien, idée) va à la file des écarts du projet.
