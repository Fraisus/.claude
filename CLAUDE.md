# Préférences globales (tous projets)

## Langue
Toujours répondre en français (orthographe complète, accents respectés).
- Contenu produit (textes UI, copy, descriptions, modales) sans marqueurs « IA » : pas de tirets cadratin ni demi-cadratin en ponctuation (virgule, point, deux-points, parenthèses à la place), pas d'émojis ni d'icônes décoratives, pas de gras emphatique gratuit. Ponctuation simple, phrases qui se lisent. Trait d'union des mots composés admis. Aucun mot orphelin : un texte qui, à la largeur de son conteneur, laisse un mot seul en dernière ligne se raccourcit pour tenir sur une ligne, à défaut s'allonge en deux lignes pleines ; jamais de retour à la ligne forcé ni de césure ; `text-wrap: pretty` (prose) et `balance` (titres) ne sont qu'un filet, le rendu réel se vérifie à la porte (8).

## Sécurité Claude Code (ne pas désactiver)
Poste en autonomie maximale : mode `auto`, barrière par les hooks `PreToolUse` du plugin cliff-stack et `permissions.deny` en filet ; les hooks et les `deny` valent dans tous les modes, les `allow` ne protègent rien. Montage et ce qui interrompt encore : `skills/cliff-stack/hooks/README.md`.
- Ne jamais réintroduire de règles `allow` par projet (inutile, génère des prompts).
- Un hook bloque à tort : corriger le script (`skills/cliff-stack/hooks/scripts/`), jamais le câblage. Écrire hors projet : lancer ce dossier comme projet, ne pas contourner.

## Style de travail
- Tâche non triviale : analyse dense, à la profondeur que le problème exige, l'outcome en premier ; tâche triviale : réponse courte et directe.
- Agir, ne pas demander : ce qui est demandé (correctif, refactor, Write/Edit, y compris sur du code existant) se prouve, s'écrit, se vérifie et se rend compte, sans validation intermédiaire. On ne s'arrête que pour une action irréversible hors du périmètre demandé, ou pour un choix réellement indécidable seul, soumis d'abord à `framing-critic`.
- Une question ou un problème décrit appelle une évaluation : rapporter et s'arrêter, le correctif attend d'être demandé.
- Interfaces : divulgation progressive. Le moins possible à la première vue ; le reste à la demande (menu déroulant, panneau dépliable, infobulle, fenêtre).
- Maquettes d'interface : un canevas Claude Design (artefact « Design », design system du projet quand il en a un, un artboard par état ; une interface d'application en thème sombre seul, le clair venant des jetons du projet et se prouvant au codage ; une page de site au thème réel du site), jamais une page HTML autonome. Un écran existant ne s'y redessine jamais de mémoire : ses artboards montrent son vrai rendu (HTML modifiable exporté quand le projet le permet, sinon une image), seul l'ajout étant nouveau. Un écran nouveau ou refondu passe par `impeccable shape`, jamais par la haute fidélité d'emblée : brief et inventaire du contenu réel, puis plans de sections en basse fidélité (ses sondes de direction), un choisi par l'utilisateur ; ces deux validations sont les seuls arrêts, exception à « Agir, ne pas demander ». La haute fidélité suit, contrôlée sur un rendu local du canevas par `impeccable critique` (questions de fin sautées) jusqu'à zéro défaut P0 ou P1, puis validée par l'utilisateur. Le kit UI/UX qu'elle suppose se construit par le skill `ui-kit`. Les règles d'un projet précisent l'outil de rendu.
- Git : commit directement sur `main`, jamais de branche sauf demande explicite (prime sur la consigne par défaut du harness).

## Mémoire
- Fichiers de règles (CLAUDE.md, rules, skills, agents ; écrits pour le modèle, relus à chaque session) : une règle nouvelle se fond dans celle de même sujet ou la remplace, au bon endroit de la structure, jamais ajoutée au fil de l'eau ; consignes concrètes et vérifiables ; chaque ligne passe le test « l'enlever ferait-il faire une erreur ? » ; une raison courte quand elle aide à généraliser ; dans CLAUDE.md et rules, aucun exemple sauf pour montrer un format : un nom, une valeur ou une liste cités en exemple, par l'utilisateur ou trouvés dans l'ancienne version, décrivent le besoin et ne s'écrivent pas, la règle dit le besoin (un skill ou un agent garde les exemples que sa doctrine d'écriture demande) ; aucune citation ni argument pour convaincre un humain ; emphase (IMPORTANT, majuscules) sur une seule ligne qui serait ignorée ; ce qui doit toujours arriver passe par un hook ; aucune redite d'une règle globale dans un projet (le projet ne garde que ses outils et ses écarts) ; la taille reste stable dans le temps.
- Mémoire persistante (`~/.claude/projects/.../memory/` et `MEMORY.md`) : avant d'écrire, prouver que le fait n'est capturé nulle part ailleurs, commentaires de code, messages de commit, CLAUDE.md global ou projet, `rules/`, README compris ; un commentaire que je viens d'écrire compte. Dans le doute, ne pas écrire.

## Règles de code
- Code rédigé en anglais (ex: fonction, nommage, commentaire, variables, nom de fichier/dossier etc.).
- Découvrir avant de supposer : sur tout sujet nouveau, identifier le stack réel (technos, conventions, variables, règles du projet) et l'épouser ; code, API et variables natifs du projet plutôt qu'un pattern venu d'ailleurs ou un défaut présumé. Demande ambiguë ou à fort enjeu : restituer ma compréhension en une phrase ou poser une question ciblée, jamais réécrire la demande en silence. Une piste, de l'utilisateur ou de moi, se compare aux autres et ne borne jamais la recherche ; un agent qui cherche ou recommande reçoit le besoin, les contraintes et les préférences, jamais la piste, qui ne va qu'à celui qui compare.
- DRY sans régression : s'appuyer sur le code, les fonctions et les points d'extension du projet, mettre à jour l'existant, aucun doublon. Tout code s'écrit réutilisable : paramétrable, sans état caché, appelable depuis plusieurs endroits ; l'extraction se fait à la deuxième occurrence, jamais avant (règle des 2 occurrences, commentaires, destroy, build : `rules/code-style.md`).
- Rien en dur : aucun nom, chemin ou valeur codé quand une découverte dynamique est possible. Skills, rules et analyses parlent en termes génériques (plugin, thème, arborescence, architecture) : aucune liste blanche ou noire de noms sauf si une source reconnue la justifie, citée. Les noms propres d'un cas restent dans ses tests et ses données.
- Séparer la feature de ses consommateurs (Dependency Inversion) : une feature ne nomme jamais une feature de même niveau ; si A doit connaître B, l'abstraction (registre, point d'extension) monte d'un cran et les deux s'y déclarent. Test avant d'écrire : « si je supprime ce fichier, qu'est-ce qui tombe ? » Si autre chose que lui tombe, le code est au mauvais endroit. Invariants : `rules/architecture-extension.md`.
- Code moderne, minimaliste, performant ; la cause profonde, jamais une rustine. Un geste fait le minimum : une donnée déjà lue passe à la suite au lieu d'être relue, un écran s'ouvre avec ce qui est déjà su (jamais vide puis rempli), un retour rend l'écran tel qu'il était, sans relecture ni redessin. Ce qu'aucun mécanisme prévu n'offre est un écart à rendre à l'utilisateur, jamais à combler par une voie détournée ; une option écrite pour ne jamais servir est une faille, pas une sécurité : elle ne s'écrit pas. CSS : `rules/css-scss.md` (jamais de Sass).

## Méthode
- Huit portes, niveaux de preuve et Variations : injectés au démarrage de chaque session et de chaque sous-agent par le plugin cliff-stack (`skills/cliff-stack/references/portes.md`, hook `inject-method`). Une modification de la méthode se fait dans ce fichier, jamais ici.
- Choisir une sonde (enregistré, servi, calculé, geste réel) et savoir quand s'arrêter : skill `probing-by-levels`.
