## 1. Composition automatique : qui l'a vraiment fait

| Qui | Comment l'équipe est déduite | Signaux | Statut |
|---|---|---|---|
| **AdaptOrch** (arXiv 2602.16873) | Un LLM décompose en sous-tâches, chacune avec coût estimé, dépendances, couplage (aucun/faible/fort/critique, notés 0/0,3/0,7/1) ; DAG ; règles fixes : parallèle si pas d'arêtes ou largeur > 0,5 et couplage ≤ 0,6 ; séquentiel si largeur 1 ; hiérarchique si couplage > 0,6 et > 5 sous-tâches ; hybride sinon. https://arxiv.org/html/2602.16873v1 | largeur du DAG, profondeur du chemin critique, densité de couplage | **[M]** papier : SWE-bench Verified 42,8 → 52,6 face au meilleur modèle seul, mais seulement +4,5 points face au meilleur baseline statique ; un Self-MoA à calcul égal récupère 89 % du gain, le routage par topologie n'explique que 11 % ; latence ×1,6. Les auteurs disent que la qualité dépend du décomposeur (erreurs propagées). Démo de recherche. |
| **Google/MIT, « Towards a Science of Scaling Agent Systems »** (arXiv 2512.08296) | Modèle prédictif qui choisit l'architecture (seul, indépendant, centralisé, décentralisé, hybride) | nombre d'outils, score du mono-agent, capacité du modèle, nombre d'agents, mesures de coordination | **[M]** 180 configurations, 3 familles de LLM : bonne architecture prédite dans 87 % des cas tenus à part (R² 0,524). https://arxiv.org/html/2512.08296v2 · https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/ |
| **AOrchestra** (arXiv 2602.03786) | Tout agent = tuple (Instruction, Contexte, Outils, Modèle) rempli à chaque pas par un orchestrateur qui crée les agents à la volée | contexte pertinent choisi par l'orchestrateur | **[M]** résumé seul : +16,28 % relatif sur GAIA, SWE-Bench, Terminal-Bench avec Gemini-3-Flash ; pas de coût chiffré dans le résumé. https://arxiv.org/abs/2602.03786 |
| **BAMAS** (arXiv 2511.21572, AAAI 2026) | Choix des LLM par programmation linéaire en nombres entiers sous budget, puis topologie par apprentissage par renforcement | budget, coût par modèle | **[M]** résumé : performance comparable à l'état de l'art, coût jusqu'à −86 % ; favorise les topologies simples sous budget serré. https://arxiv.org/abs/2511.21572 |
| **Cursor** (« scaling agents ») | Planificateurs qui explorent le code et créent les tâches, peuvent lancer des sous-planificateurs par zone (récursif) ; ouvriers sans vue d'ensemble ; juge en fin de cycle | exploration du code par le planificateur ; déclenchement des sous-planificateurs non décrit | **[R]** usage réel interne, des milliers de milliards de jetons : navigateur ~1 M de lignes en une semaine, migration Solid → React en 3 semaines « passant la CI mais à relire ». Un rôle d'intégrateur a « créé plus de goulots qu'il n'en résolvait ». https://cursor.com/blog/scaling-agents |
| **Cognition (Devin)** | Manager qui lance des Devins enfants (« map-reduce-and-manage ») ; « Smart Friend » où le modèle principal appelle un plus fort comme outil | jugé par le manager / le principal | **[R]** production. Règle retenue : écritures sur un seul fil, les autres agents apportent de l'intelligence, pas des actions. Les essaims d'écrivains parallèles ne marchent toujours pas. https://cognition.com/blog/multi-agents-working |
| **oh-my-claudecode** | Routage par palier de modèle (Haiku simple, Opus complexe), mots déclencheurs (`ralph`, `ralplan`), mais l'équipe reste explicite (`/team`) ; pipeline plan → prd → exec → verify → fix | mots du prompt ; mécanisme non documenté dans le README | **[A]** « Automatic delegation - Right agent for the job, every time » sans règle publiée ; économie 30-50 % de jetons citée par un tiers sans source. https://github.com/Yeachan-Heo/oh-my-claudecode · https://emelia.io/hub/oh-my-claudecode-multi-agent |
| **claude-flow / ruflo** | Reine + topologies hiérarchique, maillée, « adaptive » ; « hooks system automatically routes tasks » | non documentés | **[A]** « Intelligent routing (89% accuracy) » sans source. Voir §5 : le lancement multi-agent n'a parfois jamais eu lieu. https://github.com/ruvnet/claude-flow |
| **agent-organizer** (VoltAgent, awesome-claude-code-subagents) | Agent en prose : lit les définitions d'agents disponibles, associe chaque sous-tâche à l'agent dont la description couvre le mieux, choisit séquentiel/parallèle/pipeline selon le graphe de dépendances, « keep it as simple as the task allows » ; signale les trous au lieu de forcer | frontmatter `name`/`description`/`tools` | **[A]** aucune mesure, et le fichier interdit lui-même d'inventer des taux de succès. https://raw.githubusercontent.com/VoltAgent/awesome-claude-code-subagents/main/categories/09-meta-orchestration/agent-organizer.md |
| **BMAD** | « Scale-adaptive » : niveaux 0-4 (README v6) puis trois pistes (Quick Flow, BMad Method, Enterprise) selon le nombre d'histoires, l'utilisateur confirme | nombre estimé de stories, complexité | **[A]** heuristique proposée puis confirmée par l'humain ; c'est un dimensionnement du **plan**, pas de l'équipe. https://www.mintlify.com/bmad-code-org/BMAD-METHOD/concepts · https://gitee.com/XD_CHAI/BMAD-METHOD |
| **wshobson/agents** | Commandes d'orchestration à équipe **fixe** par type (ex. full-stack : architecte backend, base de données, frontend, sécurité, déploiement, observabilité), points d'approbation humains | type de commande choisi par l'humain | **[R]** source promotionnelle. https://www.vibeindex.ai/plugins/wshobson/agents/full-stack-orchestration |

Verdict §1 : la composition automatique **mesurée** n'existe qu'en recherche (AdaptOrch, Google, AOrchestra, BAMAS), avec des gains modestes face à un bon baseline fixe. En usage réel (Cursor, Cognition), la composition vient d'un planificateur LLM au sein d'une **topologie fixée par l'humain**. Les frameworks Claude Code communautaires affichent l'automatisme sans en publier la règle ni la mesure. Signal le plus solide et le plus simple : la **forme du graphe de dépendances** (largeur, couplage) et la **décomposabilité** de la tâche (Google : multi-agent −39 à −70 % sur tâches séquentielles, +80,8 % sur tâches parallélisables, [M]).

## 2. Escalade et désescalade dynamiques

Signaux employés par ceux qui l'ont tenté :
- **Blocage / boucle** : Osmani tue un agent bloqué « 3+ iterations on the same error » et réattribue à un agent frais ; `MAX_ITERATIONS=8` ; réflexion obligatoire avant chaque nouvel essai. [A] (recette, pas de mesure) https://addyosmani.com/blog/code-agent-orchestra/
- **Budget** : pause automatique à 85 % du budget de jetons par agent et notification au chef (Osmani, repris par le guide Bruniaux). [A] https://raw.githubusercontent.com/FlorianBruniaux/claude-code-ultimate-guide/main/guide/workflows/agent-teams.md
- **Inactivité** : hooks `TeammateIdle` / `TaskCompleted` qui relancent l'agent tant que tests/lint échouent ; relecteur automatique sur chaque `TaskCompleted`. [A] (Osmani)
- **Saturation du contexte** : un agent seul sur 50K+ lignes remplirait 80-90 % de son contexte, trois agents ~40 % chacun ; seuil de décision « moins de 5 fichiers = agent seul ». [A] chiffre attribué à atcyrus.com, sans protocole (guide Bruniaux).
- **Score composite** : AgentSpawn (arXiv 2602.07072) lance un enfant quand S = 0,30·interdépendance de fichiers + 0,20·complexité cyclomatique + 0,25·cascade d'échecs de tests + 0,15·occupation du contexte + 0,10·incertitude (logprobs) dépasse 0,7 ; la métrique dominante choisit la spécialité ; transmission par « SpawnPackage » (tranche de mémoire filtrée par pertinence > 0,5, compétences, contexte, tâche, métriques déclenchantes) et retour par « ResumePackage » (sortie, diffs, trace). Plafonds : profondeur 3, 4 enfants. **Mais** la conclusion du papier range « implementing the AgentSpawn prototype » dans le travail futur, les chiffres se contredisent (34 %, 97 %, 49 %) et les poids sont « proposed » : à classer **[A]**, utile seulement comme liste de signaux candidats. https://arxiv.org/html/2602.07072
- **Escalade de capacité, pas de nombre** : Cognition « Smart Friend », le modèle principal décide seul d'appeler un plus fort quand c'est « tricky enough » ; le calibrage de cette décision est dit « open problem », et ça échoue quand le principal est trop faible (SWE-1.5 + Sonnet 4.5). [R] https://cognition.com/blog/multi-agents-working
- **Planificateur récursif** : Cursor, sous-planificateurs lancés par zone, déclencheur non décrit ; le juge décide en fin de cycle de continuer, et le cycle suivant repart **à neuf** contre la dérive. [R]
- **Risque** : « Spawn Freely, Act Sparingly » (arXiv 2609.01035) : lancer des branches librement dans un bac à sable, mais n'accorder l'autorité d'agir (envoi, déploiement) qu'avec un budget de risque débité à l'activation. Théorique et synthétique. https://arxiv.org/abs/2609.01035

Qui décide : chef LLM (Cursor, Cognition, Gas Town « Mayor »), règle chiffrée (Osmani, AgentSpawn), ou humain (BMAD confirme la piste ; Gas Town met les convois « staged » en revue avant lancement, détection des agents bloqués **sur demande** de l'humain : https://kilo.ai/docs/code-with-ai/gastown/mayor).

Transmission d'état : liste de tâches partagée + fichiers de passation nommés (agent-organizer), « beads » persistants (Gas Town), paquets explicites (AgentSpawn), fourche du contexte complet (Smart Friend). Aucune source ne documente le passage d'un sous-agent **en cours** vers un coéquipier : le guide officiel cité par les tiers dit seulement de redemander explicitement une équipe, donc un redémarrage. https://code.claude.com/docs/en/agent-teams

Désescalade : **personne ne la documente comme mécanisme**. Les équivalents observés : ouvriers qui meurent à la fin de leur tâche (oh-my-claudecode : « Workers spawn on-demand and die when their task completes »), remise à zéro de cycle (Cursor), mise à mort d'un agent bloqué (Osmani), préférence pour des topologies plus simples sous budget serré (BAMAS, [M]). Pratiquant : 42 agents consolidés en 13 (commentaire de lecteur, [R]) https://joseparreogarcia.substack.com/p/claude-code-agent-teams

## 3. Contre-arguments (l'automatisme ici est une erreur)

- **La vérification est le goulot** : « The bottleneck is no longer generation. It's verification » (Osmani) ; Willison : « the natural bottleneck on all of this is how fast I can review the results », il ne peut intégrer qu'un changement significatif à la fois. [R] https://simonwillison.net/2025/Oct/5/parallel-coding-agents/
- **Le multi-agent dégrade le séquentiel et amplifie les erreurs** : −39 à −70 % sur tâches séquentielles ; agents indépendants ×17,2 d'amplification d'erreurs contre ×4,4 en centralisé ; au-delà de ~45 % de réussite du mono-agent, la coordination rend peu ou négatif ; surcoût 58 % (indépendant) à 515 % (hybride) ; capacité de raisonnement par agent trop mince au-delà de 3-4 agents à budget fixe. **[M]** https://arxiv.org/html/2512.08296v2
- **Écrivains parallèles** : Cognition maintient en 2026 que les essaims d'écrivains parallèles échouent (décisions implicites contradictoires de style, cas limites, motifs) ; managers trop prescriptifs, enfants qui ne remontent rien par défaut, état partagé supposé à tort. [R] https://cognition.com/blog/multi-agents-working
- **Les échecs viennent de la conception du système** : MAST, 14 modes en 3 familles (spécification, désalignement entre agents, vérification), 1600+ traces sur 7 frameworks, κ = 0,88 ; correctifs superficiels insuffisants. **[M]** https://arxiv.org/html/2503.13657v2
- **Pairs à égalité** : Cursor, 20 agents avec verrous tombent au débit de 2-3 ; sans hiérarchie, agents frileux qui évitent les tâches dures ; trop de structure = fragilité. [R]
- **Orchestration plutôt qu'autonomie** (Mike Mason, janvier 2026) : DORA 2025 cité, +9 % de bugs, +91 % de temps de relecture, +154 % de taille de PR ; METR, mainteneurs 19 % plus lents en se croyant 20 % plus rapides **[M]** ; Gas Town « extremely alpha », a fusionné des PR malgré des tests d'intégration en échec [R]. https://mikemason.ca/writing/ai-coding-agents-jan-2026/
- **Équipe fixe et petite** : 3 à 5, « three focused teammates consistently outperform five scattered ones » (Osmani, [A]) ; « anything more than three feels like overkill » (https://getpushtoprod.substack.com/p/30-tips-for-claude-code-agent-teams, [R]) ; > 5 agents = coordination > productivité (guide Bruniaux, [A]) ; claude-flow conseille lui-même < 8.
- **Démarrer seul, n'ajouter qu'à quatre déclencheurs** (Parreño García) : dépassement d'une fenêtre de contexte même avec sous-agents, besoin d'outils ou contraintes différents, sous-tâches indépendantes où le temps mural compte, critique indépendante d'un agent qui n'a pas vu le raisonnement. [A] https://joseparreogarcia.substack.com/p/claude-code-agent-teams
- **Humain sur le plan** : « far cheaper to fix a bad plan than to fix bad code » (Osmani) ; Gas Town et BMAD mettent l'humain entre le plan et le lancement.
- **Contexte généré par LLM** : fichiers AGENTS.md générés par LLM, ~−3 % de réussite et +20 % de coût ; écrits par un développeur, ~+4 % (Gloaguen et al., ETH Zurich, cité par Osmani). [M] selon citation, papier non relu ici.
- **Coût réel d'un bogue de lancement** : issue #55586, un seul appel crée 10 à 151 coéquipiers dupliqués invisibles (v2.1.75 à 2.1.126, Windows 11 et WSL2), jusqu'à 389 agents simultanés, ~86 Md de jetons attribués à la duplication selon le rapporteur ; causes suspectées : plusieurs lancements dans un tour, perte d'appartenance à l'équipe après compaction qui pousse le chef à relancer, relances automatiques. Fermée « not planned » le 25/08/2026. [R] https://github.com/anthropics/claude-code/issues/55586

## 4. Pratiques de consensus à conserver

- **Un fichier, un propriétaire** : Osmani (« Never let two agents edit the same file »), getpushtoprod #25, Cognition (un seul écrivain), Bruniaux (frontières de fichiers sans recouvrement).
- **Plan validé avant le code** : Osmani (le chef a rejeté un plan sans migration de base), getpushtoprod #17, Gas Town (convois staged), BMAD, Anthropic cité par Mason (« plan, then act »).
- **Vérificateur à contexte vierge** : Cognition (relecteur sans contexte partagé, ~2 bogues par PR dont ~58 % graves, [R]), Osmani (relecteur en lecture seule, 1 pour 3-4 constructeurs), Parreño García (4e déclencheur), getpushtoprod #27.
- **Worktrees** : Osmani, Conductor (un worktree et une branche par tâche, https://www.conductor.build/docs/concepts/git-worktrees), dev.to (primitive d'isolation standard au T2 2026, https://dev.to/terminalblog/orchestration-topology-is-the-new-bottleneck-in-agentic-coding-487g).
- **Budgets et bornes** : itérations, temps et jetons plafonnés (Osmani), plafonds de profondeur et de concurrence (AgentSpawn, Cursor implicite), pause à 85 %.
- **Brief complet** : la délégation vague est l'échec n°1 du schéma orchestrateur (Parreño García) ; le « téléphone arabe » des sous-agents qui n'ont qu'un résumé (Cognition 2025, https://jxnl.co/writing/2025/09/11/why-cognition-does-not-use-multi-agent-systems/).
- **Modèle par rôle** : Cursor (GPT-5.2 meilleur planificateur, Opus 4.5 « stops earlier and takes shortcuts »), getpushtoprod #10, oh-my-claudecode.
- **Repartir à neuf** périodiquement contre la dérive (Cursor) ; tuer et réattribuer un agent bloqué (Osmani).
- **Retirer de la complexité** : « Many gains came from removing complexity » (Cursor) ; « keep it as simple as the task allows » (agent-organizer).

## 5. Frameworks communautaires : ce qu'ils font vraiment

- **claude-flow / ruflo** (74,6k étoiles, ~713 issues ouvertes, 355 PR) : composition et topologie « adaptive » affirmées, non documentées. Historique de lancements qui n'ont pas lieu : #368 (juillet 2025) « hive-mind spawn did not actually use a swarm », le mainteneur finit par dire que la coordination passe par des instructions injectées dans un seul Claude Code, fermée sans changement ; #212 paramètres ignorés, toujours 4 agents codés en dur ; #955 `--claude` documenté mais sans effet ; #943 outil MCP absent ; #899 agents lancés par MCP non enregistrés dans le routeur de messages ; #1391 préfixe d'outils MCP faux dans le prompt des agents ; #2269 drapeau de permissions perdu, les runs sans tête ne peuvent pas écrire ; #655 lancement bloqué, ouvriers inactifs. https://github.com/ruvnet/ruflo/issues/368 · https://github.com/ruvnet/claude-flow/issues/212 · https://github.com/ruvnet/ruflo/issues/955 · https://github.com/ruvnet/claude-flow/issues/943 · https://github.com/ruvnet/claude-flow/issues/899 · https://github.com/ruvnet/ruflo/issues/1391 · https://github.com/ruvnet/ruflo/issues/2269 · https://github.com/ruvnet/claude-flow/issues/655 . Fiabilité apparente : faible ; succès affiché alors que l'étape n'a pas eu lieu (inférence de ma part à partir des issues).
- **oh-my-claudecode** (39,9k étoiles) : routage par palier de modèle et mots déclencheurs ; Team explicite, pipeline à étapes fixes avec boucle verify/fix ; ouvriers tmux éphémères, jusqu'à 5 selon un tiers ; mode natif dépendant de `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`, repli non-équipe sinon. Ni escalade ni désescalade documentées. Fiabilité : non évaluable (3 issues ouvertes affichées, compte peu crédible pour ce volume ; page de releases vide).
- **SuperClaude** (23,9k étoiles, v4.3.0, 61 issues ouvertes) : « Automatic coordination based on context » sans mécanisme publié dans le README actuel ; niveaux de profondeur de recherche choisis par l'utilisateur. https://github.com/SuperClaude-Org/SuperClaude_Framework
- **BMAD** : dimensionne la profondeur du plan (pistes), choisie par heuristique puis confirmée par l'humain ; pas d'escalade d'équipe. Schéma des niveaux instable d'une version à l'autre.
- **Conductor** (Melty Labs, Mac) : parallélisme humain de sessions isolées en worktrees, aucune composition ni escalade. https://www.conductor.build
- **wshobson/agents** : équipes fixes par commande, approbations humaines ; décomptes de plugins incohérents d'une source à l'autre.
- **Gas Town** (Yegge) : Mayor persistant qui décompose en beads avec dépendances, convois revus avant lancement, triage des agents bloqués sur demande ; « extremely alpha » selon l'auteur (cité par Mason). Version Kilo : https://kilo.ai/docs/code-with-ai/gastown/mayor
- **Agent teams de Claude Code** (base de P2, cité ici pour ses bogues communautaires) : #55586 (doublons, Windows inclus, fermé not planned), #40270 (échec de lancement par condition de course sur le mode de coéquipier, repli in-process), #29293 (prompt initial jamais remis, in-process compris, corrigé mars 2026). https://claudeissues.com/issue/40270-bug-agent-teams-agent-tool-with-team-name-parameter-fails-with-internal-error · https://claudeissues.com/issue/29293-bug-agent-teams-teammates-fail-to-spawn-with-input-must-be-provided-either-throu

## Implications pour le but

1. La composition automatique la plus défendable est une règle sur le graphe de dépendances (largeur, couplage, chemin critique), pas un routeur LLM opaque : c'est ce qui est mesuré (AdaptOrch, Google), et le gain face à une bonne équipe fixe est faible : l'automatisme doit surtout savoir dire « une session seule ».
2. Tâche séquentielle ou à fort couplage, ou mono-agent déjà bon : rester en P0/P1 ; c'est le seul résultat mesuré solide et il contredit l'instinct « plus d'agents ».
3. Signaux d'escalade réutilisables, tous mesurables par hook : mêmes erreurs répétées (3 itérations), budget à 85 %, dépendance inter-zones découverte (fichier hors zone touché), contexte saturé, cascade d'échecs d'essais. Aucun n'a de seuil validé publiquement : les traiter comme réglables et journalisés.
4. Personne ne promeut un sous-agent vivant en coéquipier : l'escalade praticable est « arrêter, écrire l'état dans un fichier (plan, tâches, diffs), relancer au palier supérieur à neuf ».
5. Désescalade non documentée ailleurs : à concevoir explicitement (fin de tâche = fin d'agent, consolidation, retour au fil unique d'écriture).
6. Garder l'humain sur le plan d'équipe et sur tout passage vers P2 ; l'escalade automatique vers plus d'écrivains parallèles est exactement le schéma que Cognition et Cursor déconseillent.
7. Un seul écrivain par fichier, vérificateur à contexte vierge, worktrees, plafonds : consensus large, à garder tels quels.
8. P2 sous Windows reste fragile (#55586 multiplie les coéquipiers après compaction, coût à 5 chiffres) : tout lancement P2 doit être compté et plafonné par un hook, pas par la consigne.
9. Ne rien emprunter à claude-flow sans preuve d'exécution : ses issues montrent un succès affiché sans lancement réel, ce que la maison interdit (« échouer visiblement »).
10. Taille par défaut 3 (5 au plus) pour les écrivains, sous le plafond maison de ~10 qui ne vaut que pour lecteurs et vérificateurs.
