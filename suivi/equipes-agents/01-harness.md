# 01 · Éclaireur harness : ce que Claude Code offre réellement pour une équipe d'agents

Sources : documentation officielle lue le 2026-10-14 par `curl` sur les pages `.md` (base `https://code.claude.com/docs/en/`). Abréviations : `SA` = sub-agents.md, `AT` = agent-teams.md, `WF` = workflows.md, `HK` = hooks.md, `ENV` = env-vars.md, `SR` = settings-reference.md, `TR` = tools-reference.md, `CSM` = cross-session-messaging.md, `AV` = agent-view.md, `SK` = skills.md, `CMD` = commands.md, `MOD` = plugins/mods/reference.md. Version locale non relevée (`claude --version` muet depuis Git Bash) ; les seuils de version cités viennent de la doc.

Trois faits qui conditionnent tout le reste :
- **Les outils Task (liste de tâches partagée) sont absents par défaut sur Opus 5.5.** Ils ne sont fournis d'office que sur « Opus 4.7, Sonnet 4.6, Haiku 4.5, and earlier models » ; ailleurs il faut `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` exporté **avant** de lancer `claude`, ou `--allowedTools TaskCreate` (TR, « Task tool availability »). Sans eux : « an agent coordinates with its team through messages instead of the shared task list », et `TaskCreated` « doesn't fire » (HK). Un sous-agent n'a les outils Task que si la session les a.
- **Agent teams = mode interactif seulement** : « In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates » (AT, Enable).
- **Constat sur ce harness même** : l'outil `Agent` exposé à cet éclaireur (sous-agent de profondeur 1, mode auto) a les paramètres `description, effort, isolation, model, prompt, run_in_background, subagent_type`, sans `name` ; et la remise passe par `SubagentHandback` (fourni « only in auto mode », TR).

## 1. Qui peut lancer quoi, et ce qui remonte

| Lanceur → lancé | Permis ? | Source |
| :- | :- | :- |
| Session principale → sous-agent | Oui. Plafond 20 en même temps (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, ne peut pas être désactivé), « no limit on the total number » ; levé sous ultracode ; un resume prend un créneau sans vérifier le plafond | SA « Concurrent subagent limit », ENV |
| Sous-agent → sous-agent | Oui, jusqu'à 3 couches sous le principal (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `1` coupe l'imbrication, ne peut être retiré). À la limite, `Agent` est retiré (un fork le garde mais il renvoie une erreur). Dans une définition de sous-agent, `Agent(type,…)` : « any type list inside the parentheses is ignored » (allowlist seulement pour `--agent`). En interactif, le lanceur attend ses sous-agents d'arrière-plan avant de finir ; en `-p`/SDK non, et le résultat tardif part au principal | SA « Let subagents spawn their own subagents », « Restrict which subagents can be spawned » |
| Sous-agent → workflow | Non : `Workflow` fait partie des outils retirés à tout sous-agent (avec `AskUserQuestion`, `EnterPlanMode`, `ScheduleWakeup`…) | SA « Available tools » |
| Sous-agent → coéquipier | Non documenté et exclu par la règle : un `name` ne crée un coéquipier que pour « a subagent that Claude spawns **from the main conversation** » | SA « Subagent names », AT « How Claude starts agent teams » |
| Coéquipier → sous-agent | Oui, mais **au premier plan seulement** : `background: true` refusé avec erreur, `run_in_background: true` échoue ou tourne silencieusement au premier plan | AT « Limitations », SA « foreground or background » |
| Coéquipier → coéquipier | Non : « No nested teams: teammates cannot spawn their own teammates. Only the lead can manage the team » ; « Lead is fixed » ; « One team per session » | AT « Limitations » |
| Workflow → agents | `agent()`, `pipeline()`, `parallel()` lancent des **sous-agents** ; aucune mention de coéquipiers (non documenté, et la règle « from the main conversation » l'exclut). Un agent de workflow qui invoque un skill `context: fork` attend son résultat (v2.1.295) | WF « What the saved script looks like », SK « Run skills in a subagent » |
| Principal → fork | `/subtask` ou type `fork` ; un fork ne lance pas d'autre fork | SA « Fork the current conversation » |
| Session → autres sessions | `claude --bg`, `/fork` (copie en session d'arrière-plan), `/background` ; puis `SendMessage`/`ListAgents` entre sessions (cross-session messaging, actif par défaut, Windows natif v2.1.234+) | AV, CSM |

Ce qui remonte au thread principal :
- **Rapport final** d'un sous-agent (premier plan : résultat de l'outil ; arrière-plan : notification de fin « in a later turn »). Le rapport est scanné et livré sous un en-tête qui dit qu'il ne porte aucune autorité (SA « Subagent output scanning »). En mode auto, le rapport passe par `SubagentHandback` et le classifieur le relit avant livraison (TR, SA « Permission modes »).
- **`PostToolUse` sur `Agent`** : `tool_response` = `status` (`completed` / `async_launched`), `agentId`, `content`, `resolvedModel`, `modelsUsed`, `totalTokens` (dernière requête seulement), `totalDurationMs`, `totalToolUseCount`, `usage`. En arrière-plan (défaut), aucun champ d'usage : `async_launched` + `outputFile`. Avec `SubagentHandback`, `content` n'est qu'une note : lire le rapport par un hook `PreToolUse`/`PostToolUse` sur `SubagentHandback` (`tool_input.message`) (HK « Agent »).
- **`SendMessage` vers `main`** : le sous-agent qui a `SendMessage` reçoit un « sibling roster » listant `main` et les agents nommés (instantané au démarrage) (SA « What loads at startup »). Un sous-agent qui relance un autre agent par `SendMessage` reçoit lui-même le résultat, pas le principal (SA « Resume subagents »).
- **Coéquipiers** : messages livrés automatiquement ; à l'arrêt, notification d'inactivité au chef avec la réponse finale, ou l'erreur d'API (AT « Context and communication »).

## 2. Escalade à chaud

- **Activer `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` en cours de session : non garanti par la doc.** Les `env` des fichiers de réglages sont réappliqués à la sauvegarde (ENV l. « Set variables in settings files » : « A running session applies new and changed values to its environment when you save the file », sauf les fonctions lues une fois au démarrage). AT ne documente le chaud que dans le sens de la coupure : passer à `0` « rereads the variable each time Claude spawns a subagent ». Dans l'autre sens, AT dit « Without that variable, no team is set up at session start, no team directories are written » et que config d'équipe et liste de tâches sont générées « at session startup ». Donc l'allumage à chaud est **à mesurer** (porte 1), pas à supposer. Retirer une variable du fichier ne la désactive qu'au relancement (ENV). Ici, éditer `settings*.json` est de toute façon une règle `ask` (CLAUDE.md global) et déclenche `ConfigChange` (bloquable, HK).
- **Un sous-agent déjà lancé ne devient pas coéquipier** : aucun mécanisme documenté. Le choix se fait à l'appel `Agent` : avec équipes actives, un appel du principal avec `name` lance un coéquipier, « unless the call is a fork or passes `isolation` on the call itself » ; un `isolation` en frontmatter ne l'empêche pas (le coéquipier tourne alors dans le dossier principal). Le chef ne se transfère pas.
- **Bascule par hook (inférence, à mesurer)** : `PreToolUse` sur `Agent` peut renvoyer `updatedInput`, qui « replaces the entire input object » (HK « PreToolUse decision control ») ; ajouter ou retirer `name`, ou ajouter `isolation`, choisirait donc sous-agent ou coéquipier au moment du lancement. Les champs `name`/`isolation`/`run_in_background` ne figurent pas dans le tableau d'entrée `Agent` de HK (seulement `prompt, description, subagent_type, model`), d'où la mesure nécessaire. Côté mods : `agent.spawn` (« `e.isTeammate` ») peut choisir le modèle ou refuser, `agent.offer` retirer un type (MOD).
- **Reprise (resume)** : un sous-agent se reprend par ID **ou nom** via `SendMessage` (sans équipes activées), avec tout son historique et le même jeu d'outils ; Explore et Plan ne se reprennent pas ; un sous-agent arrêté par l'utilisateur (`x`) ne se relance pas sur message ; si un nom a été réattribué, l'envoi est refusé (SA « Resume subagents »). Coéquipier in-process arrêté : un message le ramène dans la même session avec sa conversation ; **après `/resume` ou `/rewind`, les coéquipiers in-process ne reviennent pas** (AT « Limitations »).
- **Ce qui survit** : transcriptions de sous-agents indépendantes de la compaction du principal et reprenables après redémarrage par resume de la même session, effacées après `cleanupPeriodDays` (SA). La liste de tâches `~/.claude/tasks/{team}/` persiste ; la config d'équipe est supprimée en fin de session (AT « Architecture »). Après compaction : sous-agents d'arrière-plan continuent (rappel injecté), contexte ajouté par hooks résumé, skills invoqués réinjectés (5 000 jetons par skill, 25 000 au total), `SessionStart` source `compact` rejoué (context-window.md « What survives compaction »). Workflow : reprenable dans la même session ; après sortie, résultats gardés et rejouables via `claude --resume` + relance ; `/background` rejoue le run (agents en cours repartent de zéro) (WF « Resume after you leave the session », AV « What carries over »).
- **Repli sans flag expérimental** : `/fork`, `/background`, `claude --bg [--agent X] [--name N]` + cross-session messaging donnent des pairs qui se parlent (texte seulement, pas de liste de tâches ni de protocole d'équipe) (AV, CSM « Limitations »). Un `/fork` emporte modèle, mode, effort et autorisations accordées.

## 3. Hooks utiles à une équipe

Communs à tous : `session_id`, `prompt_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `permission_mode`, `effort.level`, `hook_event_name`, et dans un sous-agent ou coéquipier in-process `agent_id`, `agent_type` (HK « Common input fields »). Exit 0 + JSON : champs appliqués ; exit 2 : blocage (stderr = raison) ; autre code : erreur non bloquante, sauf `onFailure: "block"` (v2.1.295, sans effet sur Stop, SubagentStop, TaskCompleted, TeammateIdle et hooks async) (HK « Exit code output »).

| Hook | Entrée propre | Effet de exit 2 / `decision: block` | Limites, notes |
| :- | :- | :- | :- |
| `SubagentStart` | `agent_id`, `agent_type` (matcher = `name` du frontmatter ; plugin : `plugin:nom`, ancrer `^…$`) | Ne bloque pas ; stderr à l'utilisateur. `additionalContext` injecté au début du contexte du sous-agent | Se déclenche aussi au resume et **à chaque nouveau message d'un coéquipier in-process** ; réinjection seulement si la copie a disparu (après auto-compaction) |
| `SubagentStop` | `stop_hook_active`, `agent_id`, `agent_type`, `agent_transcript_path`, `last_assistant_message`, `background_tasks`, `session_crons` | `block` + `reason` : le sous-agent continue, `reason` devient son instruction suivante ; `additionalContext` : idem sans étiquette d'erreur | Plafond 8 continuations consécutives (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`, `0` = sans plafond), remis à zéro à chaque appel d'outil. Se déclenche aussi pour des agents internes (`agent_type` vide ou agent de session). Avec `SubagentHandback`, `last_assistant_message` n'est pas le rapport. Pour injecter dans le **parent** : `PostToolUse` sur `Agent` |
| `PreToolUse` `Agent` | `tool_input` : `prompt`, `description`, `subagent_type`, `model` (documentés) | `deny` / `ask` / `allow` / `defer`, `updatedInput`, `additionalContext` ; précédence deny > defer > ask > allow | Lancer un sous-agent ne demande pas de permission en soi (TR) : ce hook est le seul garde au lancement |
| `PostToolUse` `Agent` | `tool_response` (voir §1) | Ne bloque pas ; `decision: block` ajoute `reason` au résultat ; `additionalContext`, `updatedToolOutput` | Arrière-plan : pas d'usage dans la réponse |
| `PreToolUse`/`PostToolUse` `SendMessage` | Champs non tabulés dans HK ; CSM cite `to`, `summary`, `notify_when_idle` | Comme tout outil | `notify_when_idle` réservé au principal et aux sessions locales. Mods : `session.send` / `session.receive` |
| `PreToolUse` `TaskCreate`/`TaskUpdate` | `tool_input` non documenté dans HK | Comme tout outil | Existe seulement si les outils Task sont présents |
| `TaskCreated` | `task_id`, `task_subject`, `task_description?`, `teammate_name?`, `team_name` (déprécié), `agent_id?` (v2.1.290) ; pas de matcher | exit 2 ou `block` : tâche supprimée, message à Claude ; `continue: false` ignoré | Ne se déclenche pas sans outils Task |
| `TaskCompleted` | mêmes champs | exit 2 : tâche non close, stderr renvoyé | Se déclenche aussi quand un coéquipier finit son tour avec des tâches en cours ; `continue: false` arrête le coéquipier seulement dans ce cas, ignoré si `TaskUpdate` déclenche |
| `TeammateIdle` | `teammate_name`, `team_name`, `agent_id?` ; pas de matcher | exit 2 : le coéquipier continue avec le stderr ; `continue: false` l'arrête | |
| `Stop` | `stop_hook_active`, `last_assistant_message`, `background_tasks` (`type` : `subagent`, `workflow`, `teammate`, `shell`…, `agent_type`, `name` du workflow), `session_crons` | `block` : Claude continue | Même plafond 8. `background_tasks` distingue « fini » de « en attente d'un travail d'arrière-plan » |
| `WorktreeCreate` | `name` | tout code non nul : création échoue ; doit imprimer le chemin (dernière ligne) | Remplace git ; `.worktreeinclude` non traité ; déclenché par `--worktree`, `EnterWorktree`, `isolation: worktree`, agents de workflow, sessions d'arrière-plan |
| `WorktreeRemove` | `worktree_path` | non nul : suppression échoue si le dossier existe encore | **Pas lancé à la fin d'un sous-agent ou d'un agent de workflow** : leurs worktrees créés par hook restent, à nettoyer soi-même |
| `ConfigChange` | `source` (`user_settings`, `project_settings`, `local_settings`, `policy_settings`, `skills`), `file_path` | bloque l'application (sauf politique) | Seul signal hook d'un changement d'`env` à chaud |
| `PreCompact`/`PostCompact` | `trigger`, `custom_instructions` / `compact_summary` | PreCompact bloque la compaction | |

Où déclarer :
- **Frontmatter de sous-agent** : tous les événements ; actifs seulement pendant que ce sous-agent tourne ; `Stop` converti en `SubagentStop` ; sous-agents de projet : seulement après confiance du dossier du fichier (un `-p` ne compte pas) ; ceux de `~/.claude/agents/` sans cette étape ; **ignorés pour les sous-agents de plugin** (`hooks`, `mcpServers`, `permissionMode`) (SA « Hooks in subagent frontmatter », HK « Hooks in skills and agents »).
- **Frontmatter de skill** : enregistrés à l'invocation et **actifs pour le reste de la session** ; `once: true` honoré seulement ici (HK « Common fields »).
- **Plugin** : `hooks/hooks.json`, actifs tant que le plugin est activé ; les hooks de réglages, politique et plugins s'appliquent aussi dans les sous-agents (HK « Hook locations »).
- Outils utiles : `asyncRewake: true` réveille Claude sur exit 2 même session inactive (HK « Run hooks in the background ») ; hook `type: "agent"` (expérimental, jusqu'à 50 tours, `{ok}`) ; un hook ou une commande peut poster dans la boîte de **sa propre session** via `CLAUDE_CODE_MESSAGING_SOCKET` (pipe nommé sous Windows, ligne d'auth `CLAUDE_CODE_MESSAGING_TOKEN` obligatoire), message « own-child » livré quand aucun `crossSessionInbound` ne s'applique (CSM « The session's inbox socket »). Mods : `$.prompt.submit({ text })` démarre un tour quand la session est inactive (plugins/mods/api.md).

## 4. Workflows dynamiques

- **Ce qu'un script fait** : JavaScript avec `await` au niveau racine ; `agent(prompt, { schema, label, stallMs, … })` (modèle par étape = modèle « per-invocation » dans l'ordre de résolution), `pipeline(liste, fn)`, `parallel()`, `phase(titre)`, `log()`, global `args` ; `meta` littéral en tête (`name`, `description`, `phases`). `agent()` renvoie `null` sur arrêt ou erreur irrécupérable ; `schema` : sortie JSON validée, 5 essais (`MAX_STRUCTURED_OUTPUT_RETRIES`), schéma contradictoire refusé avant lancement. Agents isolables en worktree (WF « Migrate many files »). Cache partagé entre agents de même préfixe, départ décalé de 5 s (`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`) (WF).
- **Ce qu'il ne fait pas** : aucune saisie utilisateur en cours de run (pauses seulement pour permissions et limite d'usage ; « For sign-off between stages, run each stage as its own workflow ») ; aucun accès direct fichier ou shell ; pas d'`import()` ; `Date.now()`, `Math.random()`, `new Date()` lèvent une exception (rejeu déterministe) ; pas de coéquipiers.
- **Bornes** : 16 agents simultanés par défaut (`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS`, 1 à 256), 4 096 éléments par `parallel`/`pipeline`, **1 000 agents par run** ; décrochage : jusqu'à 5 redémarrages (`stallMs`, `CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS`, 10 min) ; pause sur limite d'usage (interactif + abonnement, deux fois au plus).
- **Écriture à la volée** : mot-clé `ultracode` ou demande en clair (« use a workflow ») dans une invite tapée par l'humain seulement (pas `-p`, pas un message relayé) ; `/effort ultracode` laisse Claude décider pour chaque tâche et lève l'avertissement de taille, le plafond de 20 sous-agents et l'approbation en mode auto. Référence d'écriture : skill `/workflow-authoring`. Script de chaque run écrit sous le dossier de session dans `~/.claude/projects/`.
- **Approbation** : invite par run (phases, script lisible, `Ctrl+G`) en Manual/acceptEdits ; en auto, seulement au premier lancement (consentement enregistré dans les réglages utilisateur) ; en `-p`, règle `Workflow` / `Workflow(<nom>)`, mode auto, hook `PreToolUse` qui autorise, ou hôte (WF « Approve the plan »). Chez l'utilisateur, `Workflow` est une règle `ask` (CLAUDE.md global).
- **`/workflows`** : liste, phases avec nombre d'agents, détail par agent (invite, appels, résultat, jetons), touches `p` pause, `x` arrêt, `r` relance d'un agent, `s` sauvegarde en `.claude/workflows/` ou `~/.claude/workflows/` (commande `/<nom>`) ; ligne de progression dans le panneau des tâches.
- **Budget** : `workflowSizeGuideline` (`small` < 5, `medium` < 10, défaut, `large` < 50) n'est qu'un **conseil** ; avertissement « Large workflow » au-delà de 25 agents ou 1,5 M jetons projetés, **purement indicatif** ; seule borne dure : 1 000 agents. Un garde de budget réel passe donc par un hook `PreToolUse` sur `Workflow` (le schéma d'entrée est dans la référence SDK TypeScript, non lue ici) et par `Stop.background_tasks` (`type: workflow`, `name`). Désactivation : `disableWorkflows`, `CLAUDE_CODE_DISABLE_WORKFLOWS` (lu au démarrage). Un run en cours continue si on désactive.

## 5. Mémoire et état partagé

- **Champ `memory`** des sous-agents : `user` → `~/.claude/agent-memory/<nom>/`, `project` → `.claude/agent-memory/<nom>/` (recommandé), `local` → `.claude/agent-memory-local/<nom>/` ; injecte les 200 premières lignes ou 25 Ko de `MEMORY.md`, active Read/Write/Edit ; sans effet si l'auto-mémoire est coupée (SA « Enable persistent memory »). La mémoire auto du principal n'atteint jamais un sous-agent non fork.
- **Liste de tâches** : `~/.claude/tasks/{team-name}/`, `team-name` = `session-` + 8 premiers caractères de l'ID de session ; états pending / in progress / completed ; dépendances (une tâche bloquée ne peut être prise, déblocage automatique) ; prise par verrou de fichier ; persiste et reste locale. Format des fichiers non documenté (à mesurer). Statut qui traîne : limite connue (AT « Assign and claim tasks », « Limitations »).
- **Boîtes aux lettres** : `~/.claude/teams/{team}/inboxes/{agent}.json`, entrées validées à la lecture ; `config.json` avec `members` (nom, ID, type ; le chef est `team-lead`), réécrit par le harness, à ne pas éditer ; aucun équivalent projet (AT « Architecture »).
- **Lisible par un hook** : tout ce qui est sur disque (transcriptions via `transcript_path` et `agent_transcript_path`, fichiers d'équipe et de tâches), identifiants `task_id`/`teammate_name`/`agent_id` dans les événements Task, `background_tasks` dans Stop/SubagentStop. Workflow : variables du script seulement, rien de partagé hors rapport final.

## 6. Modèle et effort par rôle

- **Sous-agent** : (1) `model` passé à l'appel, (2) frontmatter `model` (`inherit` = principal), (3) `CLAUDE_CODE_SUBAGENT_MODEL`, (4) modèle principal ; un mod `agent.spawn` remplace (1). Un alias de la famille du principal prend le modèle exact du principal (avec `[1m]`). Le modèle passé à l'appel survit au resume (SA « Choose a model »).
- **Coéquipier** : modèle nommé dans l'invite de lancement, puis définition, puis variable, puis modèle du chef ; figé au lancement ; `/model` depuis la vue d'un coéquipier agit sur le chef (AT « Specify teammates and models »).
- **Agent de workflow** : même ordre, le modèle fixé par le script comptant comme modèle d'appel (WF « Cost »).
- **`CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`** (v2.1.257) : ignore frontmatter et modèle d'appel pour sous-agents, coéquipiers et agents de workflow ; sans la variable modèle, prend le modèle principal (Explore garde le sien) ; forks et skills `context: fork` à `model: inherit` restent sur le principal.
- **Effort** : `CLAUDE_CODE_EFFORT_LEVEL` > `effort` passé à l'appel (non fork, v2.1.292, survit au resume) > frontmatter `effort` > effort de session (SA « Choose an effort level ») ; coéquipiers : effort du chef par défaut, `effort` de la définition appliqué en in-process (AT). La réflexion étendue suit la session. Skill : `model`/`effort` du frontmatter valent pour le tour seulement (SK).
- **Cache** : requêtes de sous-agents, agents de workflow et coéquipiers in-process hors du seau du principal, **5 min par défaut même sur abonnement** ; ordre : `FORCE_PROMPT_CACHING_5M` > `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` > `subagentPromptCacheTtl` > frontmatter `experimental.cacheTtl` > `ENABLE_PROMPT_CACHING_1H` ; `1h` facturé plus cher (SR, prompt-caching.md « Choose the TTL yourself »). Un fork réutilise le cache du principal ; un resume relit le cache du run initial.

## 7. Windows

- Coéquipiers : panneaux séparés seulement avec tmux ou iTerm2, « not supported in VS Code's integrated terminal, Windows Terminal, or Ghostty » : **in-process seulement** (AT « Limitations »).
- Cross-session messaging : v2.1.234+ en natif ; pipe nommé, ligne d'auth obligatoire ; une session WSL 2 et une session Windows natives ne se joignent pas ; pas de preuve de processus pour les messages « own-child », seul le jeton vérifie (CSM).
- Hooks : `"shell": "powershell"` (pwsh puis powershell.exe) ; écrire `${CLAUDE_PROJECT_DIR}` ou `$env:CLAUDE_PROJECT_DIR`, jamais `$CLAUDE_PROJECT_DIR` nu ; pas de `/dev/tty` (HK « Windows PowerShell tool »).
- Worktrees : suppression sans suivre jonctions ni liens (v2.1.205) ; une autorisation « don't ask again » reste attachée au worktree sous Windows ; en worktree isolé, les commandes PowerShell n'ont que le contrôle du dossier de travail, pas celui des redirections git réservé à Bash (SA « Write subagent files », worktrees.md).
- Divers : Glob/Grep de repli pour sous-agents seulement hors Windows natif (SA) ; `processWrapper` ignoré ; agent view : `←` ambigu juste après attache, superviseur bloqué à tuer par `taskkill /PID` (AV) ; `Alt+W` écarte le mot-clé ultracode (WF).

## Implications pour le but (escalade P1 → P2 en cours de run)

1. L'escalade ne peut pas « promouvoir » un sous-agent : P2 se crée par de **nouveaux** lancements `Agent` nommés depuis le principal ; l'état passe par fichiers ou transcription repris, pas par le contexte vivant.
2. Seul le thread principal peut monter en P2 : sous-agents, agents de workflow et coéquipiers ne peuvent ni créer ni gérer d'équipe ; un détecteur en profondeur doit **remonter un signal** (rapport, `SendMessage` à `main`, `SubagentStop`/`PostToolUse Agent`, socket propre, `asyncRewake`).
3. Allumer `AGENT_TEAMS` à chaud est non documenté (doc : mise en place « at session start ») et passe par un `ask` sur les réglages : à mesurer avant tout plan ; plus sûr de démarrer la session avec équipes actives et de laisser `name` absent tant qu'on reste en P1, puis d'ajouter `name` (éventuellement via `updatedInput` d'un hook, à mesurer).
4. Sous Opus 5.5, la liste de tâches partagée et `TaskCreated` n'existent que si `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` est exporté au lancement : sinon P2 = messages seuls, et les hooks Task sont muets.
5. P2 impossible en `-p`/SDK et après `/resume` (coéquipiers non restaurés) : une escalade automatique doit vivre dans une session interactive et tolérer la perte des coéquipiers.
6. P1b ne peut pas escalader seul : pas de saisie en cours de run, pas de coéquipiers ; il faut finir le workflow et relancer depuis le principal (rejeu des agents terminés).
7. La redescente est simple et documentée : `AGENT_TEAMS=0` relu à chaque lancement, arrêt des coéquipiers par demande d'arrêt ou `TaskStop`.
8. Garde de budget : seuls 1 000 agents par run et 20 sous-agents simultanés sont des bornes dures ; tout le reste (taille, « Large workflow ») est indicatif, donc le garde doit être un hook `PreToolUse` sur `Agent`/`Workflow`.
9. Windows : P2 en in-process uniquement ; coéquipiers sans worktree, donc partition des fichiers obligatoire.
